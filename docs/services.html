Shared foundations

Four mechanisms every process depends on identically. Described once here, referenced from each service below.

Two classes of table

ClassTablesRLSWritten by
Reference
shared by all hospitals		drug, shortage_event, drug_price, rxnorm_edgenoingest
Tenant
owned by one hospital		formulary_item, stock_snapshot, job, recommendation, review_decision, audit_log_entry, mapping_specyesapi, worker

Reference data is polled once for every hospital — why the cost curve is sub-linear in site count. Tenant data never leaves its hospital, enforced by row-level security, not application code.

Tenant context is set, never filtered

Every process declares who it's acting as before touching a tenant table:

SET LOCAL app.hospital_id = '…';
SET LOCAL app.actor_id    = '…';

api reads both from the verified JWT. worker reads hospital_id from the job row, sets actor_id = 'system:worker'. ingest sets them per hospital when enqueuing, and touches reference tables outside any tenant context. The app connects as a role without BYPASSRLS, and one that doesn't own the tables — an owning role ignores its own policies.

Consequence

The background path is not a privilege backdoor. A bug in worker cannot read another hospital's formulary any more than a bug in api can.

The audit log writes itself

"We remember to call audit()" is the same weak guarantee as "we remember to write WHERE hospital_id." So it's a trigger, reading the actor from the same session settings — append-only is a grant, not a convention:

-- fires on every state change, reads current_setting('app.actor_id' / 'app.hospital_id')
CREATE TRIGGER audit_review_decision
  AFTER INSERT OR UPDATE ON review_decision
  FOR EACH ROW EXECUTE FUNCTION write_audit_entry();

REVOKE UPDATE, DELETE ON audit_log_entry FROM app_role;

The job table is the only queue

CREATE TABLE job (
  id           bigserial PRIMARY KEY,
  hospital_id  uuid NOT NULL,
  type         text NOT NULL,        -- match | extract | mapping_spec
  dedupe_key   text NOT NULL,
  payload      jsonb NOT NULL,
  status       text NOT NULL DEFAULT 'pending',  -- pending|running|done|failed
  attempts     int  NOT NULL DEFAULT 0,
  locked_at    timestamptz,
  last_error   text,
  created_at   timestamptz NOT NULL DEFAULT now(),
  UNIQUE (type, dedupe_key)
);

No Redis, no Pub/Sub. At tens of jobs an hour, a broker is an extra pod, an extra failure mode, and an extra thing to explain. UNIQUE (type, dedupe_key) is what makes producers idempotent — a CronJob that runs twice inserts the same key twice, and the second insert is a no-op.

Talks to

Browser (inbound, via Ingress) — and nothing else server-side. web serves the shell and static assets; the browser calls api directly on the same origin.

Why not proxy through web

Routing API traffic through the Next.js server adds a hop, forces token forwarding through Node, and makes web an availability dependency of every data request. Same-origin means the session cookie is httpOnly, Secure, SameSite=Lax — and no CORS configuration exists anywhere.

Lifecycle

Stateless. Readiness = process is up. Any replica can be killed at any moment with no in-flight state to lose. Rolling update, maxUnavailable: 0.

The rule that shapes this service

api never calls the LLM — not once, on any path. A request that needs model output enqueues a job and returns 202 with a job id; the UI polls. Even the connector-factory spec proposal, the one place a human is genuinely waiting on a model, is still a job — the alternative is a request thread blocked 30 seconds and an HPA whose CPU metric means nothing. Payoff: one external dependency (Postgres), p99 in the tens of milliseconds, and an LLM outage degrades the system to "no new recommendations," not "the application is down."

The dequeue loop

UPDATE job SET status = 'running', locked_at = now(), attempts = attempts + 1
WHERE id = (
  SELECT id FROM job
  WHERE attempts < 5
    AND (status = 'pending'
         OR (status = 'running' AND locked_at < now() - interval '10 minutes'))
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING *;

One query dequeues, reclaims work abandoned by a crashed worker, and caps retries — no separate reaper process; the stale-running branch is the reaper.

Transaction discipline

The lock is not held across the LLM call: UPDATE … RETURNING commits immediately (job now running), then the LLM is called with no transaction open, then a fresh transaction writes the result and flips status='done'. Holding a row lock across a multi-second network call would mean long-lived transactions and a vacuum problem for zero benefit — locked_at already provides the mutual exclusion.

Crash safety

A pod preempted mid-call leaves the job running with a stale locked_at; another replica reclaims it after 10 minutes, attempts incremented. After 5 attempts the job lands in failed, surfaced with last_error. Writes are idempotent — recommendation carries UNIQUE (shortage_event_id, formulary_item_id, candidate_drug_id) — so a reclaimed job re-writes rather than duplicates.

Scaling — the load-profile argument

worker is latency-bound, not CPU-bound: a replica spends most of a job blocked on an LLM response. A saturated worker with 40 queued jobs shows near-zero CPU, so CPU-target HPA doesn't work — the correct signal is queue depth.

triggers:
  - type: postgresql
    metadata:
      query: "SELECT count(*) FROM job WHERE status = 'pending'"
      targetQueryValue: "5"

minReplicaCount: 1, maxReplicaCount: 3 — bounded by LLM spend, not nodes. Load arrives in bursts (FDA publishes a batch, forty formulary items go at-risk in the same minute) — precisely the shape docker-compose can't serve, since it scales the host, not the one saturated process.

OPEN  KEDA is an extra operator to learn. Fallback if it costs more than half a day: fix replicas: 2, keep the KEDA manifest unapplied in the repo, demonstrate elastic behaviour with kubectl scale against a seeded queue.

ingest

CronJob

hourly · no Service object, no inbound traffic at all

schedule: "17 * * * *"     # off the hour — everyone else polls at :00
concurrencyPolicy: Forbid   # a slow run must not overlap the next
startingDeadlineSeconds: 300
activeDeadlineSeconds: 900
backoffLimit: 2

Responsibility

Pull the outside world in, and decide what changed. Per run, per feed:

  1. Fetch — conditional request where the source supports it; a 304 skips the rest.
  2. Normalize — vendor payload → canonical reference row.
  3. Upsert — ON CONFLICT (source, source_id) DO UPDATE, natural keys only.
  4. Diff — an unchanged shortage produces no downstream work.
  5. Fan out — each newly at-risk formulary item, across all hospitals, gets a match job, dedupe_key = shortage_event_id:formulary_item_id.
  6. Record — one feed_run row per feed, read by the ops dashboard.

Failure isolation & idempotency

Each feed runs inside its own try/except — a failure records feed_run.status='error' and continues; the Job exits non-zero only if every feed failed. The CronJob will run twice (Spot preemption mid-run, a missed schedule caught by startingDeadlineSeconds) — every write is a natural-key upsert, every enqueue is ON CONFLICT DO NOTHING. A duplicate run produces zero duplicate rows and zero duplicate LLM spend.

Not ingest's job

Hospital CSV import arrives through api (POST /formulary/import) — a human is attached to it and needs synchronous validation feedback. ingest never receives inbound traffic.
