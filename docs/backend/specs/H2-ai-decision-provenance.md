# H2 — AI decision provenance

**Owner:** `shared/medstock_shared/ai.py` + `ai_tasks.py` · **Flows:** 7, 12, 18, 19 · **Status:** ✅ (wave 6)
**Depends on:** H1

## Goal

`dedupe_key` is `sha256(task + "\x00" + canonical_json(payload))` — the question, and only the
question. Edit a prompt and the key is unchanged, so every user keeps receiving answers
generated by the previous prompt, forever, with no record of which prompt produced what.

That is two defects in one: a **caching bug** (a fixed prompt never takes effect) and an
**audit hole** (an AI-attributed decision cannot be reproduced). For a product whose
differentiator is auditability, the second is the serious one.

## Changes

### 1. `AITask` carries its version

```python
@dataclass(frozen=True)
class AITask:
    name: str
    owner: str
    prompt: str
    prompt_version: str                 # bump on every prompt edit — this is the contract
    model: str = "gemini-..."           # pinned per task, not a global
    validate: Callable[[dict], None] | None = None
```

A CI check fails the build when `prompt` changes in a diff without `prompt_version` changing.
Without that check this decays to a field nobody remembers to bump.

### 2. The key includes them

```python
def dedupe_key(task: str, payload: dict, prompt_version: str, model: str) -> str:
    canonical = json.dumps(payload, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(
        f"{task}\x00{prompt_version}\x00{model}\x00{canonical}".encode()
    ).hexdigest()
```

A prompt edit now misses cache and regenerates — correct behaviour. Old rows stay readable as
history rather than being served as current answers.

### 3. `ai_cache` records them

```sql
ALTER TABLE ai_cache ADD COLUMN model          text NOT NULL DEFAULT '';
ALTER TABLE ai_cache ADD COLUMN prompt_version text NOT NULL DEFAULT '';
```

The unique constraint stays `(type, dedupe_key)` — the key already encodes both, so the columns
are for querying and for the export, not for identity.

### 4. The audit log points at the answer

`ask_ai()` sets `app.ai_dedupe_key` (`SET LOCAL`) for the surrounding transaction. Any row H1's
trigger writes during that transaction carries the key, so D3's export can join an AI-attributed
decision to the exact stored model output.

## Rules

1. `model` is pinned per task, not read from one global env var. Two tasks should be able to
   move to a new model independently, and a model change must invalidate that task's cache.
2. Never store the rendered prompt in `ai_cache`. Prompts live in code under version control;
   the row stores which version, not a copy that drifts.
3. `payload` must stay free of volatile values — a timestamp or a request id in the payload
   destroys the cache. This is already documented in `ask_ai`'s docstring; add an assertion in
   tests, not a runtime scan.
4. No backfill. Existing rows keep empty strings and age out; rewriting history to look
   provenanced is precisely the thing this feature exists to prevent.
5. `ai_cache` stays global — no `hospital_id`, no RLS. The payload behind the key is reference
   data, never PHI, and cross-tenant sharing is the point of the cache.

## Acceptance criteria

- [x] Editing a prompt and bumping `prompt_version` produces a cache miss and a new row.
- [x] Editing a prompt without bumping fails CI.
- [x] Two tasks on different models produce different keys for the same payload.
- [x] A `review_decision` created from an AI recommendation has `ai_dedupe_key` set on its audit row.
- [x] That key resolves to exactly one `ai_cache` row.
- [x] Existing rows keep working (empty defaults, no migration failure).

## Out of scope

Storing token counts or latency per call, prompt A/B testing, an eval harness for prompt
regressions, per-tenant model overrides.
