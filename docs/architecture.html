Solution Architecture — GCP Deployment

Formulary & supply intelligence for hospital pharmacies. Two logical blocks — WEB and API — deployed as eight always-on workloads plus three scheduled ingest CronJobs on a single GKE cluster, over one Postgres database. Three GCP-managed services, one model provider. Sized to fit inside a $200 education credit for the length of the capstone.

Architecture

Box fill encodes who operates the component — us, GCP, or the outside world. Numbers match the data-flow walkthrough below. The one deliberately unfinished edge is drawn, not hidden: nothing polls the public feeds yet.

What runs where

Eight always-on Deployments, plus three ingest CronJobs that only run on their own schedule. All the Python ones are built from one Dockerfile — they differ by env, route, or (for ingest) command, not by build.

Data flow

Numbered against the diagram above.

  1. Hospital user opens the app. Browser → Ingress over HTTPS, carrying a JWT with hospital_id and role.
  2. Ingress serves the UI from web — the application shell and static assets, nothing else.
  3. The browser calls the seven services directly on the same origin, /api/*. Each verifies the JWT locally with a public key it already holds — auth is not on the request path — then opens a transaction with SET LOCAL app.hospital_id. Postgres row-level security does the tenant filtering; no hand-written WHERE hospital_id = … exists anywhere.
  4. analogue and prediction call ask_ai() directly — no job, no queue, no poll. It checks ai_cache first (UNIQUE (type, dedupe_key) — the same question is free the second time, across every hospital, not just the one that asked it); on a miss it calls Gemini inline, with backoff on 429/5xx and a 20 s timeout, and validates the answer before caching it — a citation must be a verbatim substring of its source text, or the call fails and the caller gets a 503. This is the one place a request thread blocks on a model call; there used to be a separate ai-handler service and queue here, removed because its real benefits (crash-survival mid-call, a hard concurrency ceiling) weren't in use at this system's volume — see the trade-off section below.
  5. Every service reads and writes the one database under RLS. State changes fire a trigger that writes audit_log_entry; that table has UPDATE/DELETE revoked at the grant level, not just by convention.
  6. Formulary and stock arrive as a CSV upload through the browser into inventory — a human is attached to it and needs synchronous validation feedback, so it is not an ingestion path.
  7. Nothing polls the public feeds yet. Drawn in red because it is still missing in practice — the ingest CronJob code exists (three scripts, one image) but isn't scheduled or migrated. Without it the system can rank alternatives but cannot notice that a drug entered shortage. See the open questions.
  8. Secrets (DB credentials, JWT keys, the Gemini key) reach pods via Workload Identity + Secret Manager — never an env file, never a log line.
  9. CI builds and deploys on merge to main: ruff, Alembic, pytest, then a build matrix of eight service images (seven domain services plus ingest) plus web, then the migration Job runs to completion, and only then does kubectl apply -k roll the Deployments.

Tenant isolation, enforced below the app

With seven services the argument gets stronger: a policy in Postgres holds in one place, an application-level filter would have to hold in seven codebases written by four people.

-- every tenant table
ALTER TABLE formulary_item ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON formulary_item
  USING (hospital_id = current_setting('app.hospital_id')::uuid);

-- ai_cache is deliberately NOT a tenant table — no hospital_id column,
-- no RLS. Reference-data Gemini answers are shared across every hospital
-- asking the same question (docs/services.md §1.1).

-- audit log: append-only is a grant, not a promise
REVOKE UPDATE, DELETE ON audit_log_entry FROM app_role;

The application role has no BYPASSRLS and does not own the tables — a role that owns a table ignores its own policies. Object-level authorization is a side effect of this, not separate code: another hospital's row is simply not visible, and the handler returns 404.

The trade we made, stated plainly

Better said by us on stage than asked by a reviewer.

This is a distributed monolith

Seven deploy units share one database and one shared/ package. The deploy boundary is real — independent rollout, isolated process failure, four developers working in parallel. The data boundary is not, and that was deliberate: prediction needs to join stock against shortages, and over HTTP that becomes pagination, retries and fake-upstream fixtures instead of the drug logic that is the actual product. The price is that a breaking change in shared/ redeploys all seven — which is why every service is built and tested on every PR.

The boundaries follow ownership, not load

compliance and analogue will never need to scale apart. The split is two services per developer. That is an honest answer and a defensible one for a four-person team on a fixed timeline — inventing a technical justification for it would not survive a follow-up question.

We removed the one workload with a different shape

There used to be a ninth workload, ai-handler, that was latency-bound rather than CPU-bound — a runner blocked on Gemini instead of doing CPU work, so CPU-target HPA couldn't see its load and queue depth would have been the right signal, had it ever been wired up. It never was: replicas stayed fixed at 2 for the service's whole life. We removed it rather than keep paying for a Deployment, a NetworkPolicy, and an async job contract for a scaling story that was never built. analogue and prediction now block their own request thread on a Gemini call instead — the honest cost of that trade is in docs/services.md §4.

Open questions

Still yours to decide — each changes real code, not just config.

Who owns scheduled ingestion, and when?

Nothing polls FDA, RxNorm or NADAC today. Without it the system can rank alternatives on demand but cannot notice a drug entering shortage — the product's core promise. The answer is a CronJob off the same image, most likely three of them (shortages hourly, pricing daily, RxNorm weekly), not a service. Decide the owner before feature work spreads polling into individual services: that path ends in eight schedules, a blown openFDA quota (1 000 req/day per IP), and no way to tell who spent it.

blocks: at-risk detection, the sub-linear cost argument

RLS policies — when do they land?

The session helper already sets app.hospital_id on every transaction, but no CREATE POLICY exists yet, and the app role must not own the tables. Until that migration ships, tenant isolation is a design, not a mechanism, and it cannot be demonstrated on stage.

first migration

Where do MVP stock numbers actually come from?

The public feeds give shortage events, not a hospital's own shelf counts — nobody publishes that. Days-of-supply math needs it. CSV upload, a generated synthetic dataset, or a mock "distributor" API you write yourselves — pick one, it changes the schema.

Does patient-profiling store PHI at all?

It is the only service that touches clinical data about identifiable people. Storing none in the MVP — de-identified aggregates only — is defensible, cheaper, and removes a category of compliance argument you would otherwise have to make on stage. Decide before schema work.

Does a user belong to one hospital, or several?

One hospital per user puts hospital_id straight in the JWT — half a day of work. Several (a hospital network, a fill-in pharmacist) moves tenancy from the user to the session: a membership(user_id, hospital_id, role) table, a hospital switcher in the UI. Hard to retrofit later.

default: one hospital/user now, role lives in membership from day one

Token lifetime and revocation?

Local verification is what keeps auth off the request path, but it also means a token stays valid until it expires — a role or hospital change does not take effect immediately, and there is no revocation list. Short TTL is the MVP answer; pick the number and say it out loud.

Does the cluster stay up, or spin up for demos?

Always-on burns credit steadily but removes cold-start risk. On-demand saves money but means proving, well before the actual defense, that eight workloads (plus ingest's CronJobs, once scheduled) reliably come back up inside your setup window.
