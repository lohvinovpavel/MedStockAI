Data flow

Numbered against the diagram above.

  1. Hospital user opens the app. Browser → Ingress over HTTPS, carrying a JWT with hospital_id and role.
  2. Ingress serves the UI (web) and routes API calls (api) on separate paths behind the same certificate.
  3. Every api request opens a transaction and runs SET LOCAL app.hospital_id — Postgres row-level security does the tenant filtering from there; no hand-written WHERE hospital_id = … anywhere in the code.
  4. ingest wakes up hourly, polls the four keyless public feeds and the hospital's own formulary/stock (CSV in the MVP).
  5. Same run imports the hospital feed into the same upsert path.
  6. When ingest finds a shortage event touching the formulary, it writes the shortage record and enqueues a match job.
  7. worker dequeues with SELECT … FOR UPDATE SKIP LOCKED — safe with multiple worker replicas, no broker required.
  8. worker calls the LLM to rank RxNorm-equivalent alternatives and pull an exact-sentence citation.
  9. Recommendation + audit entry are written to Postgres; the audit table has UPDATE/DELETE revoked at the grant level, not just by convention.
  10. Secrets (LLM key, DB credentials) reach every pod via Workload Identity + Secret Manager — never an env file, never a log line.
  11. Logs and metrics from every pod flow to Cloud Logging/Monitoring.
  12. CI builds and pushes on merge to main: GitHub Actions runs tests + the golden-set eval, then pushes an image to Artifact Registry, which the cluster pulls on kubectl apply.

Tenant isolation, enforced below the app

The filter lives in Postgres, not in application code — so a missed WHERE clause in some future report can't leak another hospital's formulary.

-- every tenant table
ALTER TABLE formulary_item ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON formulary_item
  USING (hospital_id = current_setting('app.hospital_id')::uuid);

-- audit log: append-only is a grant, not a promise
REVOKE UPDATE, DELETE ON audit_log_entry FROM app_role;

Open questions

Still yours to decide — each changes real code, not just config.

Does a user belong to one hospital, or several?

One hospital per user puts hospital_id straight in the JWT — half a day of work. Several (a hospital network, a fill-in pharmacist) moves tenancy from the user to the session: a membership(user_id, hospital_id, role) table, a hospital switcher in the UI. Hard to retrofit later.

default: one hospital/user now, but role lives in membership from day one

Where do MVP stock numbers actually come from?

The four public feeds give shortage events, not a hospital's own shelf counts — nobody publishes that. Days-of-supply math needs it. CSV upload, a generated synthetic dataset, or a mock "distributor" API you write yourselves — pick one before ingest gets built, it changes the schema.

Auth: roll your own JWT, or an external IdP?

Own JWT is faster to ship. An IdP (Firebase Auth, Auth0 free tier) reads better against "secure authentication" in the evaluation criteria and hands you MFA/password-reset for free.

Does the cluster stay up, or spin up for demos?

Always-on burns credit steadily but removes cold-start risk. On-demand saves money but means proving, well before the actual defense, that it reliably comes back up inside your setup window.
